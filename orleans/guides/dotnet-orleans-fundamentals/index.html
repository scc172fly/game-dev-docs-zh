1. 类是设计图，对象才是运行时的东西#

C#
var a = new Helper();
var b = new Helper();

a.Coins = 100;
Console.WriteLine(b.Coins); // 0，不是 100
Console.WriteLine(ReferenceEquals(a, b)); // False

public sealed class Helper
{
    public int Coins { get; set; }
}

Helper 是类（类型）；a、b 是引用变量；执行 两次 new，就有两个不同的实例。即使这两个实例的代码、初始属性值完全相同，对象身份依然不同。属性值相等 ≠ 两个引用指向同一个对象。

C#
var a = new Helper();
var b = a; // 没有 new

a.Coins = 100;
Console.WriteLine(b.Coins); // 100
Console.WriteLine(ReferenceEquals(a, b)); // True

这一回 a 和 b 指向同一个对象。这是理解 Scoped、Singleton 的第一块地基。

区分两种“相同”：`a.Coins == b.Coins` 比较值；`ReferenceEquals(a, b)` 比较两个变量是否引用同一个对象。对于引用类型，`==` 可能被重载，讨论生命周期时优先用 `ReferenceEquals` 验证身份。

2. 构造函数什么时候执行？#

C#
var x = new Helper(); // 创建 Helper #1
var y = new Helper(); // 创建 Helper #2
var z = x;            // 不会调用构造函数

public sealed class Helper
{
    private static int _next;
    public int Id { get; }

    public Helper()
    {
        Id = ++_next; // 为简化示例；并发环境应使用 Interlocked
        Console.WriteLine($"创建 Helper #{Id}");
    }
}

构造函数负责在创建实例时初始化实例。GetReward() 等普通方法被调用，不会因此重新执行构造函数。后面讲 Transient 时，“每次解析一次”与“每次调用方法一次”的区别特别重要。

3. 字段是对象持有的引用#

C#
public sealed class InventoryLogic
{
    private readonly Helper _helper;

    public InventoryLogic(Helper helper)
    {
        _helper = helper; // 只是保存引用，没有创建新的 Helper
    }
}

两段相同的构造函数代码，可以接收相同对象，也可以接收不同对象，完全取决于调用方给了什么参数。

1. 把“能力”与“具体做法”拆开#

C#
public interface IRewardCalculator
{
    int Calculate(int level);
}

public sealed class FixedRewardCalculator : IRewardCalculator
{
    public int Calculate(int level) => level * 10;
}

public sealed class DoubleRewardCalculator : IRewardCalculator
{
    public int Calculate(int level) => level * 20;
}

IRewardCalculator 定义“能够计算奖励”；两个类提供不同算法。接口不能直接 new，必须有实现。

C#
var normal = new PlayerLogic(new FixedRewardCalculator());
var doubleReward = new PlayerLogic(new DoubleRewardCalculator());

Console.WriteLine(normal.Gain(5));       // 50
Console.WriteLine(doubleReward.Gain(5)); // 100

public sealed class PlayerLogic
{
    private readonly IRewardCalculator _calculator;

    public PlayerLogic(IRewardCalculator calculator)
    {
        _calculator = calculator;
    }

    public int Gain(int level) => _calculator.Calculate(level);
}

PlayerLogic 依赖的是接口约定，不依赖某一个具体奖励算法。只要某个对象实现该接口，构造函数都能接收。

2. “依赖”和“注入”具体指什么？#

  • 依赖（Dependency）：PlayerLogic 要完成工作，必须使用一个 IRewardCalculator。
  • 注入（Injection）：在构造 PlayerLogic 时，从外部把计算器对象传进去。
  • 控制反转（IoC，Inversion of Control）：把“谁来决定和创建依赖”的控制权，从使用者自身移交给外部组装代码或框架。依赖注入（DI）是实现 IoC 的常见方式。

注意：new PlayerLogic(new FixedRewardCalculator()) 本身就使用了构造函数注入。有 DI 不等于一定有 DI 容器。

3. 控制反转（IoC）：真正反转的是谁的控制权？#

通行译法是“控制反转”，不是“反转控制”。这个概念听起来抽象，实际只是在问：谁决定 PlayerLogic 要使用哪个计算器？

修改前 · 自己掌握控制权

PlayerLogic 在内部 new FixedRewardCalculator()，所以自己决定用哪种算法。

修改后 · 由外部组装

PlayerLogic 只声明需要 IRewardCalculator；外部决定给固定奖励还是双倍奖励。

C#
// 没有控制反转：PlayerLogic 自己决定依赖类型
public sealed class PlayerLogic
{
    private readonly IRewardCalculator _calculator;

    public PlayerLogic()
    {
        _calculator = new FixedRewardCalculator();
    }
}
C#
// 外部的组装代码决定用哪一种实现
var player = new PlayerLogic(new FixedRewardCalculator());

// 有控制反转：PlayerLogic 只声明所需能力
public sealed class PlayerLogic
{
    private readonly IRewardCalculator _calculator;

    public PlayerLogic(IRewardCalculator calculator)
    {
        _calculator = calculator;
    }
}

这时反转的是“创建/选择依赖的控制权”，而不是把程序运行顺序倒过来。手动把依赖作为构造参数传进去已经可以实现 DI；使用容器只是进一步自动化组装与生命周期管理。

不要混淆：IoC 是更广泛的设计思想；DI 是一种具体实现办法；DI 容器是实现 DI 的工具。三者不等同，也不要求每个业务类都实现一个接口。
思考题 · 先自己判断

在 new PlayerLogic(new FixedRewardCalculator()) 中，没有使用 DI 容器。它是否仍然属于依赖注入？为什么？

点击查看参考答案

属于。依赖通过构造函数由外部传入，PlayerLogic 不再负责创建计算器，所以它是构造函数注入。DI 是一种组装方式，不以是否使用容器为前提。

4. 什么时候使用接口？#

希望替换实现、隔离外部依赖、便于测试时，接口非常适合；纯粹的小型内部对象，不必为了“DI”机械地创建无意义接口。

思考题 · 先自己判断

如果把 PlayerLogic 的构造参数从 IRewardCalculator 改成具体类型 FixedRewardCalculator，后来又想换成双倍奖励算法，需要改动哪里？

点击查看参考答案

如果构造函数强制要求 FixedRewardCalculator，那么传入的对象必须是这个类型（或它的子类）；换成另一种无继承关系的计算器时，就需要改 PlayerLogic 的构造参数等代码。保留接口 IRewardCalculator 后，只需让新算法实现接口并改变外部组装/注册规则，PlayerLogic 无须跟着修改。

先看结论：主构造函数把“创建对象需要的参数”写在类名后面。它没有取消构造过程，也没有替你注册服务。先读懂普通写法，再用简写，不需要为了“新”而改写所有类。

    }
}

两段的这次输出相同：你好，我是 小明。不过，不能因此说两种写法在所有方面都完全相同：第一段有显式 readonly 字段，第二段的参数没有这个限制。

把类名后的 (string name) 读成一句话：“创建一个 Player，需要外面给我一个名字。” 调用方仍写 new Player("小明")；不是把类变成了方法，也不是调用 SayHello() 时再传名字。

依据：微软：声明主构造函数。这是 C# 12 起提供的语法；本教材的 .NET 10 项目可使用。

字段没写，参数到底保存在哪里？#

普通构造函数的局部参数不能直接拿到另一个方法里用，所以传统代码要执行 _name = name。

主构造函数允许实例成员使用参数。编译器看到 SayHello() 以后还要读取 name，就为它安排隐藏存储。是编译器帮你保存，不是这个值凭空一直存在。

下面只是帮助理解的展开示意，不是精确反编译结果：

C#
public sealed class Player
{
    // 示意名称。真实隐藏字段不叫这个名字。
    private string _capturedName;

    public Player(string name)
    {
        _capturedName = name;
    }

    public void SayHello()
    {
        Console.WriteLine($"你好，我是 {_capturedName}");
    }
}

记住：少写字段声明，不等于对象不再保存数据。 对 ILogger<T> 这类引用类型，保存的是传入对象的引用，不是复制一份日志对象。

如果参数只用来初始化你自己声明的字段，就不必再为该参数保留一份额外隐藏字段：

C#
public sealed class Player(string name)
{
    private readonly string _name = name;

    public void SayHello()
    {
        Console.WriteLine(_name);
    }
}

这里后续方法统一用 _name。不要一会儿读 _name，一会儿又在实例方法里读 name，否则可能出现两份存储，让维护者难以判断该用哪一份。

参数、字段、属性：这三个东西不要混成一个#

以 public sealed class Player(string name) 为例：

写法 能不能用？ 原因
实例方法里写 Console.WriteLine(name) 可以 直接使用主构造函数参数
写 this.name 不可以 普通 class 的主构造参数不是名为 name 的成员
外部写 player.name 不可以 没有自动声明可访问的同名属性
自己声明 public string Name { get; } = name; 可以 明确创建了一个属性，外部可读 player.Name

需要公开名字时，自己写出来：

C#
public sealed class Player(string name)
{
    public string Name { get; } = name;
}

此处参数只参与初始化 Name；属性会有自己的存储。普通 class 和位置参数式 record 的规则不同，别把后者自动生成属性的行为套到所有类上。

对应官方规则：参数不是成员、不会为普通类自动生成属性。

readonly 到底保护什么？#

主构造参数可以重新赋值。以下是独立的完整控制台示例：

C#
var player = new Player("小明");

Console.WriteLine(player.GetName()); // 小明
player.Rename("小红");
Console.WriteLine(player.GetName()); // 小红

public sealed class Player(string name)
{
    public void Rename(string newName)
    {
        name = newName;
    }

    public string GetName()
    {
        return name;
    }
}

readonly 字段则限制字段本身在构造完成后被重新赋值。对于服务引用，它防止你把字段改为指向另一个服务，不代表被引用对象内部的数据不可修改，也不自动保证线程安全。

例如，private readonly List<int> _items = new(); 仍然允许 _items.Add(1)，但不能在普通实例方法里执行 _items = new List<int>()。

依据：微软：readonly 字段。删除显式 readonly 字段时，需要知道你放弃了这项编译期限制。

回到 HeartbeatWorker：逐个拆开类声明#

C#
public sealed class HeartbeatWorker(
    ILogger<HeartbeatWorker> logger) : BackgroundService
{
    protected override Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        logger.LogInformation("后台任务启动");

        return Task.CompletedTask;
    }
}

这段只用来演示声明，执行一次就结束，不是周期心跳程序。持续运行的完整版本在第 16 章。

部分 读成什么
HeartbeatWorker 我们定义的类名
(ILogger<HeartbeatWorker> logger) 创建对象时需要的构造参数
: BackgroundService 继承 BackgroundService
logger.LogInformation(...) 使用创建对象时传进来的日志对象

冒号表达的是继承，不是“把 logger 传给 BackgroundService”。要给需要参数的基类传值，才会出现 : SomeBase(logger) 这样的形式。

注册仍然是：

C#
builder.Services.AddHostedService<HeartbeatWorker>();

语法和对象来源分开看：主构造函数由 C# 编译器处理；DI 容器根据构造参数找服务；Host 管理后台服务启动。把传统构造函数改成主构造函数，不会自动改变注册、Scope 或服务生命周期。

官方也用 Worker 展示这种重构：使用主构造函数重构代码。

三种写法怎么选？给这本教材定一条规则#

本教材的建议，而不是强制标准：先用传统写法理解原理；简单注入类优先用主构造函数；需要编译器限制字段重新赋值时保留 readonly；初始化步骤较多时用传统构造函数。 已有项目风格一致，比机械追求代码最短更重要。

场景 建议 理由
初次理解参数怎样存入对象 传统构造函数 创建、接收、保存三步都看得见
HeartbeatWorker、简单 Logic，只接收并使用依赖 主构造函数，直接用参数 减少重复声明和赋值
团队要求依赖引用必须是只读字段 主构造函数 + readonly 字段，或传统写法 保留编译期约束
构造时有多步验证、日志、初始化 传统构造函数 执行顺序更直观
Orleans Grain 需要异步初始化 使用激活阶段处理 主构造函数和传统构造函数都不能写成 async 构造函数

三种写法并排比较时，只改变保存依赖的表达方式：

A．传统构造函数。

C#
public sealed class PlayerService
{
    private readonly IRewardCalculator _calculator;

    public PlayerService(IRewardCalculator calculator)
    {
        _calculator = calculator;
    }

    public int GetReward(int level)
    {
        return _calculator.Calculate(level);
    }
}

B．主构造函数，直接用参数。

C#
public sealed class PlayerService(
    IRewardCalculator calculator)
{
    public int GetReward(int level)
    {
        return calculator.Calculate(level);
    }
}

C．主构造函数，保留 readonly 字段。

C#
public sealed class PlayerService(
    IRewardCalculator calculator)
{
    private readonly IRewardCalculator _calculator = calculator;

    public int GetReward(int level)
    {
        return _calculator.Calculate(level);
    }
}

这三段沿用本章 IRewardCalculator.Calculate(int level) 接口；同名类每次只采用一种。不要为了所谓“更快”改写；这里的选择主要是可读性和只读约束，不是性能优化。

思考题：B 没有写字段，是否完全不用保存 calculator？点击查看答案

不是。GetReward 会在对象创建后使用 calculator，编译器需要保存它的引用。它仍然是主构造函数参数，不会自动成为能用 this.calculator 访问的成员，也不自动具有 readonly 限制。

思考题：改成主构造函数后，Transient 会变成 Singleton 吗？点击查看答案

不会。主构造函数改变的是源码写法；复用规则由服务注册决定。无论使用哪种构造函数，Transient 注入一次后如果被对象保存，后续调用方法都继续使用原来拿到的那份引用。

1. 尖括号 <T>：类型也是参数#

C#
var a = new Box<int>(100);
var b = new Box<string>("玩家1001");

public sealed class Box<T>
{
    public T Value { get; set; }

    public Box(T value) => Value = value;
}

T 是类型参数。IOptions<RewardOptions> 表示“管理 RewardOptions 的选项接口”；ILogger<PlayerGrain> 表示“以 PlayerGrain 为日志类别的日志服务”。

2. 委托：把方法当作参数#

C#
static int Double(int x) => x * 2;

Func<int, int> operation = Double;
Console.WriteLine(operation(3)); // 6

Func<int,int> 的最后一个类型参数是返回值，前面的类型参数是输入参数。Action<T> 表示没有返回值的方法。

3. Lambda =>：匿名函数的简短写法#

C#
Func<int, int> a = x => x * 2;
Func<int, int> b = x =>
{
    int result = x * 2;
    return result;
};

x 是参数名，不是关键字；=> 可以读成“接收 x，执行右边的内容”。它并不代表异步，也不等于执行了函数，只是表达一段可以被调用的逻辑。

以后看到：

C#
services.AddSingleton<IRewardCalculator>(sp =>
    new FixedRewardCalculator());

要读成“把一个接收 sp、返回计算器对象的创建函数传给注册方法”。

4. 扩展方法：为什么对象‘凭空’多了一个 AddSingleton？#

C#
Console.WriteLine("Hello".WithMark()); // Hello!

public static class TextExtensions
{
    public static string WithMark(this string value)
    {
        return value + "!";
    }
}

扩展方法是静态方法的调用语法糖，并非真的修改了 string。上面的代码等价于 TextExtensions.WithMark("Hello")。AddSingleton、UseOrleans、Configure 等很多 API 也是扩展方法。

记忆技巧：在 IDE 中找不到某个 `.AddXxx()` 方法时，先查看 `using`，再寻找它所在的静态扩展类；它很可能不是 `builder` 本身定义的方法。

1. Task 表示一个异步操作#

C#
static async Task<int> LoadCoinsAsync()
{
    await Task.Delay(300); // 模拟等待 I/O
    return 500;
}

int coins = await LoadCoinsAsync();
Console.WriteLine(coins);

Task<int> 表示以后会得到一个 int 结果。await 等待这个任务完成，不意味着为每次 await 新建线程。在服务器程序里，数据库和网络调用经常返回 Task 或 ValueTask。

2. await 之前、之后仍然是一个方法#

C#
public async Task<int> GiveRewardAsync()
{
    Console.WriteLine("开始");
    await Task.Delay(100);
    Console.WriteLine("继续执行");
    return 100;
}

await 是等待点；它不会重新创建 this、字段，也不会重新运行构造函数。Transient 的生命周期不由 await 或方法调用控制。

3. CancellationToken：协作式取消#

C#
static async Task LoopAsync(CancellationToken token)
{
    while (!token.IsCancellationRequested)
    {
        Console.WriteLine("检查任务");
        await Task.Delay(1000, token);
    }
}

取消是通过令牌协调，Task.Delay 在取消后可能抛 OperationCanceledException，通常代表预期的取消而非程序崩溃。

4. IDisposable：作用域结束时释放资源#

C#
using (var resource = new DemoResource())
{
    Console.WriteLine("使用资源");
} // 离开 using 块调用 Dispose()

public sealed class DemoResource : IDisposable
{
    public void Dispose() => Console.WriteLine("资源已释放");
}

Dispose 用来及时释放外部资源，不等于垃圾回收器立刻回收对象内存。后面会看到：由容器创建并管理的服务，应让容器在合适的时机释放。

看懂 catch 后面的 when：满足条件才处理#

在 Worker 中常见下面这段（放在异步方法内部）：

C#
try
{
    await Task.Delay(
        TimeSpan.FromSeconds(2),
        stoppingToken);
}
catch (OperationCanceledException)
    when (stoppingToken.IsCancellationRequested)
{
    // 关闭令牌已取消，把本次等待取消当作正常退出。
}

把它读成：“异常属于取消异常，并且 Host 的关闭令牌已取消，才进入这个 catch。”

when 是异常筛选器，不是循环，也不负责触发取消。条件不满足时，这个 catch 不处理异常，运行时继续寻找其他处理者。上面的条件只检查关闭令牌的状态，并不是严格证明所有取消异常都由这个令牌造成；复杂的多令牌业务要按实际意图区分。

依据：微软：when 异常筛选器。

await using：等待的是释放，不是“异步创建 Scope”#

C#
await using (var scope = scopeFactory.CreateAsyncScope())
{
    var job = scope.ServiceProvider
        .GetRequiredService<ICleanupJob>();

    await job.RunAsync(stoppingToken);
}

// 执行到这里时，Scope 的异步释放已经完成。

这段是使用模式，scopeFactory、ICleanupJob 的来源和注册见完整 Worker 示例。按顺序理解：创建 Scope → 取出任务 → 等任务执行 → 离开大括号时等待释放。

这里 CreateAsyncScope() 直接返回一个 AsyncServiceScope，不是返回待等待的 Task。await using 让离开范围时调用并等待 DisposeAsync()。

带大括号的写法在这对大括号结束时释放；await using var scope = ...; 声明式写法在所在代码块结束时释放。放在方法体里与放在循环体里，范围可能不同。不要以为读完下一行就释放了。

依据：微软：using 语句与 using 声明。普通控制流退出和异常退出都会执行相应清理；这不是进程被强制终止时的保障。

思考题：一次 await 会自动重新创建 Transient 依赖吗？点击查看答案

不会。await 只是异步等待点，不会重新执行构造函数，也不会自动向容器解析依赖。已经存入字段或被主构造参数捕获的引用仍然是原来的引用。

1. 一台机器上可以有多个 Host / Silo#

文本
机器 A
  ├── 进程 1：Host A → DI 容器 A → Silo A
  └── 进程 2：Host B → DI 容器 B → Silo B
机器 B
  └── 进程 3：Host C → DI 容器 C → Silo C

若每个容器都注册一个 Singleton<SharedConfig>，通常会分别拥有一个单例对象。Singleton 不表示“全世界只有一个”，更不表示“整个 Orleans 集群一个”。

2. 四个容易混淆的‘生命周期’#

事物 什么时候创建或开始 通常什么时候结束
进程 操作系统启动程序 进程退出
Host builder.Build() Host 被释放、进程结束
DI Scope CreateScope() 或框架创建 Scope 被释放
普通服务对象 首次解析 / 每次解析 / 显式构造 引用消失后可被 GC 回收，或被容器释放

对象的逻辑生命周期不等于 GC 立即释放内存的时刻。Scoped 常常是在 Scope 销毁时执行 Dispose，并不是在每次方法返回时释放。

3. 线程安全与共享实例#

C#
public sealed class BadCounter
{
    public int Value;
    public void AddOne() => Value++; // 并发调用下不是安全的原子操作
}

如果将带可变状态的 BadCounter 注册成 Singleton，多个 Grain 可以同时使用它，不能依赖 Grain 默认的单激活调度来保护跨 Grain 的共享对象。

对于无状态服务，单例通常更容易处理；对于需要可变状态的共享服务，需要锁、原子操作、并发结构，或者重新设计所有权。

4. Task 不等于线程#

Task 是异步工作/结果的抽象。一个任务可能等待数据库而暂时不占用工作线程，也可能在线程池上执行计算。不要把 Task.Run 当成所有异步操作的唯一方式。

2. 为什么叫 Resolve（解析）？#

→

4. 容器内部是怎么递归“找到并创建”的？#

把核心原理缩写成一个教学版的 Resolve 函数，就很好理解了。下面代码不是 Microsoft DI 的真实源码，只演示根据注册映射递归检查构造函数参数的过程；暂不实现 Scope、Singleton 缓存、释放与特殊工厂注册等机制。

C#
// 需要 using System.Collections.Generic;
// 需要 using System.Linq;

// 服务类型 -> 具体实现类型
var registrations = new Dictionary<Type, Type>
{
    [typeof(GameSettings)] = typeof(GameSettings),
    [typeof(IRewardCalculator)] = typeof(RewardCalculator),
    [typeof(PlayerLogic)] = typeof(PlayerLogic)
};

object Resolve(Type requestedType)
{
    // [1] 找到服务对应的实现类型
    Type implementationType = registrations[requestedType];

    // [2] 找到要执行的构造函数
    var constructor = implementationType.GetConstructors().Single();

    // [3] 对每个构造参数，再递归调用 Resolve
    object[] arguments = constructor.GetParameters()
        .Select(parameter => Resolve(parameter.ParameterType))
        .ToArray();

    // [4] 参数准备齐了，才真正创建当前对象
    return constructor.Invoke(arguments);
}

// 假设 GameSettings、RewardCalculator 和 PlayerLogic
// 是上一段代码中定义的三个具体类型。
var player = (PlayerLogic)Resolve(typeof(PlayerLogic));
Console.WriteLine(player.GetReward());

真实的 .NET 默认容器实现会更复杂：它建立解析规则（调用站点），针对 Singleton 和 Scoped 管理复用缓存，处理工厂注册、IEnumerable<T>、开放泛型、循环依赖和 IDisposable 对象，并优化执行过程。它不一定在每次请求时重新做上面这段反射遍历。教学版只展示你最需要理解的“递归拼好依赖图”的思路。

6. IServiceProvider 本身能不能注入？从哪里得到？#

可以注入。它是容器提供的框架服务，可以作为构造函数参数，就像请求 ILogger<T> 一样。host.Services、scope.ServiceProvider 是另外两种访问已有服务提供程序的入口，不是让你自己 new IServiceProvider()。

C#
using Microsoft.Extensions.DependencyInjection;

var services = new ServiceCollection();
services.AddScoped<DemoHelper>();
services.AddScoped<ScopeReporter>();

using var provider = services.BuildServiceProvider(
    validateScopes: true);

using var scope = provider.CreateScope();
var reporter = scope.ServiceProvider
    .GetRequiredService<ScopeReporter>();
reporter.PrintHelperId();

public sealed class DemoHelper
{
    public Guid Id { get; } = Guid.NewGuid();
}

public sealed class ScopeReporter
{
    private readonly IServiceProvider _provider;

    // IServiceProvider 由容器自动传进来
    public ScopeReporter(IServiceProvider provider)
    {
        _provider = provider;
    }

    public void PrintHelperId()
    {
        // 在这里获取的 Scoped 服务属于当前 Scope
        var helper = _provider.GetRequiredService<DemoHelper>();
        Console.WriteLine(helper.Id);
    }
}

这段程序可以运行，但把 IServiceProvider 存进业务类只是为了让你观察其来源。普通业务逻辑中通常不要照此设计。更清晰的写法是直接声明真实依赖：

C#
public sealed class ScopeReporter
{
    private readonly DemoHelper _helper;

    public ScopeReporter(DemoHelper helper)
    {
        _helper = helper;
    }

    public void PrintHelperId()
    {
        Console.WriteLine(_helper.Id);
    }
}
非常关键的边界：如果容器在某个 Scope 中创建 ScopeReporter，它注入的 IServiceProvider 关联这个 Scope；如果注入给 Singleton，则通常是根提供程序。根提供程序不应拿来随意解析 Scoped 对象。IServiceProvider 可以注入，并不等于应该在所有业务类中注入。

什么叫服务定位器（Service Locator）反模式？就是一个类的构造函数只写 IServiceProvider，但它的方法内部四处调用 GetRequiredService<A>()、GetRequiredService<B>()。调用方只看构造函数，根本看不出这个类还需要 A 和 B。与之相比，直接注入 A、B 可读性更好、也更方便编写单元测试。

思考题 · 先自己判断

如果一个 GlobalManager 是 Singleton，它的构造函数里直接注入 IServiceProvider。它随后使用该 Provider 解析 Scoped 服务，这样是不是“自动有了一个新 Scope”？

点击查看参考答案

不是。注入给 Singleton 的一般是根容器提供程序。它不会因为调用一次 GetRequiredService 就自动创建一个子 Scope。要在单例中执行 Scoped 工作，应注入 IServiceScopeFactory，明确创建并及时释放 Scope。

Console.WriteLine(ReferenceEquals(a, b)); // False

// 内层：DemoHelper 是 Scoped，同一个 Scope 中复用。
Console.WriteLine(ReferenceEquals(a.Helper, b.Helper)); // True

public sealed class DemoHelper
{
}

public sealed class QuestLogic(DemoHelper helper)
{
    public DemoHelper Helper { get; } = helper;
}

把它展开成普通 C#，大致就是：

C#
var sharedHelper = new DemoHelper();

var a = new QuestLogic(sharedHelper);
var b = new QuestLogic(sharedHelper);

两个不同的“外壳”，完全可以引用同一个内部工具。 所以比较对象时，要明确比较的是 a 与 b，还是 a.Helper 与 b.Helper。

同一个容器、同一个 Scope 内，保持 QuestLogic 为 Transient，仅替换 Helper 的注册：

Helper 注册方式 ReferenceEquals(a, b) ReferenceEquals(a.Helper, b.Helper)
Singleton False True
Scoped False True
Transient False False

Singleton 和 Scoped 在这一个 Scope 中表现相同；换到另一个 Scope，Scoped 的 Helper 会换一份，Singleton 仍复用。 这张表中的 True 不代表 Scoped 就变成了 Singleton。

构造函数声明的是“需要什么类型”，并不决定传入哪个实例。容器分别满足两个构造参数时，会查看 DemoHelper 的注册。同一个 Scope 内若它是 Scoped，就传入同一份；若按类型注册为 Transient，就分别创建。代码长得一样，不等于参数引用相同。

3. 为什么 Singleton 不应该直接捕获 Scoped？#

C#
services.AddScoped<PlayerContext>();
services.AddSingleton<GlobalManager>();

public sealed class GlobalManager
{
    public GlobalManager(PlayerContext context) { }

问题：GlobalManager 要活整个容器生命周期，而 PlayerContext 应该只在一个 Scope 内存活。单例持有短生命周期对象，会导致生命周期错配（Captive Dependency）。开启 Scope 验证时，容器会对此类依赖抛出异常。

正确方向：重新设计接口边界；若单例确实需要执行某个有作用域的操作，应借助 IServiceScopeFactory 为每次操作建立独立 Scope，再在范围内使用和释放服务。不要简单通过关闭验证掩盖问题。

4. IServiceScopeFactory 从哪里来，怎么使用？#

答案：由默认 DI 容器内置提供。IServiceScopeFactory 是一个专门负责创建 Scope 的服务，容器会提供它（单例生命周期），你不需要写 AddSingleton<IServiceScopeFactory, ...>()。

对比下面的代码：GlobalManager 是 Singleton，PlayerContext 是 Scoped。GlobalManager 不保存某个长期存在的 PlayerContext，而是每次工作都新建一个 Scope。

C#
using Microsoft.Extensions.DependencyInjection;

var services = new ServiceCollection();
services.AddScoped<PlayerContext>();
services.AddSingleton<GlobalManager>();

using var provider = services.BuildServiceProvider(
    validateScopes: true);

var manager = provider.GetRequiredService<GlobalManager>();
manager.ExecuteOnce();
manager.ExecuteOnce();

public sealed class PlayerContext
{
    public Guid Id { get; } = Guid.NewGuid();
}

public sealed class GlobalManager
{
    private readonly IServiceScopeFactory _scopeFactory;

    public GlobalManager(IServiceScopeFactory scopeFactory)
    {
        // 不必手动注册 IServiceScopeFactory
        _scopeFactory = scopeFactory;
    }

    public void ExecuteOnce()
    {
        // [1] 新建此次操作专属的作用域
        using var scope = _scopeFactory.CreateScope();

        // [2] 在新作用域内部解析 Scoped 服务
        var a = scope.ServiceProvider
            .GetRequiredService<PlayerContext>();
        var b = scope.ServiceProvider
            .GetRequiredService<PlayerContext>();

        // [3] 本次 a、b 相同；下次 ExecuteOnce 会换实例
        Console.WriteLine($"同一个 Scope？{ReferenceEquals(a, b)}");
        Console.WriteLine($"本次 PlayerContext：{a.Id}");

        // [4] 方法结束，using 自动释放整个 Scope
    }
}

预期输出中，两次 同一个 Scope？ 都是 True。但两次 ExecuteOnce() 打印的 PlayerContext.Id 通常不同，因为每调用一次就新建一个 Scope。

SingletonGlobalManager
→
ExecuteOnce [1]Scope A → Context A
/
ExecuteOnce [2]Scope B → Context B

它为什么比“Singleton 直接持有 Scoped”安全？因为单例只保存长期可用的作用域工厂，不把某个 Scoped 对象作为长期字段。每次操作内部创建短作用域，操作完成后自动释放。

5. 异步任务为什么用 CreateAsyncScope？#

如果操作有 await，而依赖对象可能实现 IAsyncDisposable，就使用 CreateAsyncScope() 配合 await using：

C#
public sealed class GlobalManager
{
    private readonly IServiceScopeFactory _scopeFactory;

    public GlobalManager(IServiceScopeFactory scopeFactory)
    {
        _scopeFactory = scopeFactory;
    }

    public async Task RunOnceAsync(CancellationToken token)
    {
        // 创建异步作用域：可以异步释放资源
        await using var scope = _scopeFactory.CreateAsyncScope();

        // ICleanupJob 是提前注册为 Scoped 的业务服务
        var job = scope.ServiceProvider
            .GetRequiredService<ICleanupJob>();

        await job.RunAsync(token);

        // 退出方法时，自动执行 Scope 的异步释放
    }
}

这一小段是调用模式演示，其中的 ICleanupJob 假设已注册。想看完整的注册、接口、实现、Worker 和启动代码，请阅读 第 16 章：完整后台服务 Scope 实战。

builder / HostApplicationBuilder 构建前 设置配置、日志及服务注册

4. Build、StartAsync、RunAsync 的区别#

  • StopAsync()：请求优雅停止并等待停止流程。

RunAsync() 通常内部负责启动和等待关闭；不要不加思考地在已经 StartAsync() 后又重复调用它。

1. Service、Hosted Service、BackgroundService 是什么关系？#

2. 完整示例：每两秒打印一次心跳#

先创建普通控制台项目并安装 Hosting 包；也可以继续使用前面的 HostLab 项目。

将 Program.cs 全部替换为下面内容。使用第 2 章的主构造函数写法，直接使用传进来的 logger：

C#
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;
using Microsoft.Extensions.Logging;

var builder = Host.CreateApplicationBuilder(args);

builder.Services.AddHostedService<HeartbeatWorker>();

using var host = builder.Build();

await host.RunAsync();

public sealed class HeartbeatWorker(
    ILogger<HeartbeatWorker> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(
            TimeSpan.FromSeconds(2));

        try
        {
            while (await timer.WaitForNextTickAsync(stoppingToken))
            {
                logger.LogInformation(
                    "服务器心跳：{Time}",
                    DateTimeOffset.Now);
            }
        }
        catch (OperationCanceledException)
            when (stoppingToken.IsCancellationRequested)
        {
            // Host 请求正常关闭，结束等待。
        }
    }
}

运行 dotnet run，大致每两秒记录一次心跳。按 Ctrl+C 后，Host 通知任务停止；取消等待时产生的取消异常被这个筛选后的 catch 处理。

沿着一条线读：注册 Worker → 构建并运行 Host → 容器传入 ILogger<HeartbeatWorker> → 后台服务执行 ExecuteAsync() → 等 Tick → 打日志 → 收到停止通知后退出。构造参数只在创建对象时提供，不是每次 Tick 都重新注入。

3. 主构造函数和传统写法，对应在哪里？#

上例的 logger 在实例方法中使用，编译器会保存其引用。它不自动具备 readonly 字段的限制。下面展示传统写法的对应结构；只用于对照，不要把它与上面的同名类一起放进项目：

C#
public sealed class HeartbeatWorker : BackgroundService
{
    private readonly ILogger<HeartbeatWorker> _logger;

    public HeartbeatWorker(ILogger<HeartbeatWorker> logger)
    {
        _logger = logger;
    }

    protected override Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        _logger.LogInformation("后台任务启动");

        return Task.CompletedTask;
    }
}

为突出构造过程，这个对照方法只执行一次。换回周期循环时，传统版用 _logger，主构造版用 logger，服务注册不变。

选择原则：简单注入用主构造函数；需要显式只读保护时保留字段；初始化步骤较多时用传统构造函数。不用为了整本书“全部一样”把教学对照也删掉。

builder.Services.AddScoped<ICleanupJob, CleanupJob>();

// 后台 Worker：由 Host 管理，注册为 Singleton。
builder.Services.AddHostedService<CleanupWorker>();

using var host = builder.Build();

await host.RunAsync();

public interface ICleanupJob
{
    Task RunAsync(CancellationToken cancellationToken);
}

public sealed class CleanupJob : ICleanupJob, IAsyncDisposable
{
    private readonly ILogger<CleanupJob> _logger;
    private readonly Guid _id = Guid.NewGuid();

    public CleanupJob(ILogger<CleanupJob> logger)
    {
        _logger = logger;
        _logger.LogInformation("创建任务：{Id}", _id);
    }

    public async Task RunAsync(CancellationToken cancellationToken)
    {
        _logger.LogInformation("开始任务：{Id}", _id);

        await Task.Delay(300, cancellationToken);

        _logger.LogInformation("完成任务：{Id}", _id);
    }

    public ValueTask DisposeAsync()
    {
        _logger.LogInformation("释放任务：{Id}", _id);

        // 演示对象没有真正的异步清理工作。
        return ValueTask.CompletedTask;
    }
}

public sealed class CleanupWorker(
    IServiceScopeFactory scopeFactory,
    ILogger<CleanupWorker> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        try
        {
            while (!stoppingToken.IsCancellationRequested)
            {
                // [1] 每轮创建新的 Scope。
                await using (var scope = scopeFactory.CreateAsyncScope())
                {
                    // [2] 只从本轮 Scope 获取任务。
                    var job = scope.ServiceProvider
                        .GetRequiredService<ICleanupJob>();

                    // [3] 等任务完成，再离开 Scope。
                    await job.RunAsync(stoppingToken);
                } // [4] 这里等待 Scope 及其对象完成异步释放。

                logger.LogInformation("本轮结束，等待下一轮");

                await Task.Delay(
                    TimeSpan.FromSeconds(3),
                    stoppingToken);
            }
        }
        catch (OperationCanceledException)
            when (stoppingToken.IsCancellationRequested)
        {
            // 关闭令牌已取消，正常退出后台循环。
        }
    }
}

正常完成一轮时，观察日志中的顺序。下面用 A、B 代替实际随机 GUID：

文本
创建任务：A
开始任务：A
完成任务：A
释放任务：A
本轮结束，等待下一轮

创建任务：B
开始任务：B
完成任务：B
释放任务：B
本轮结束，等待下一轮

看见的重点不是编号长什么样，而是每轮“创建—执行—释放”成套出现。 在执行中取消时，可能没有“完成任务”这一行，但正常的异常退出仍会经过 await using 的清理。示例未捕获其他业务异常；真实任务的重试、告警和失败策略要另行设计，不能用一个空 catch (Exception) 全部吞掉。

6. 把最绕的三行拆开读#

C#
await using (var scope = scopeFactory.CreateAsyncScope())
{
    var job = scope.ServiceProvider
        .GetRequiredService<ICleanupJob>();

    await job.RunAsync(stoppingToken);
}
表达式 直白意思
scopeFactory.CreateAsyncScope() 新建本轮独立的服务共享与释放范围
scope.ServiceProvider 通过这个新范围获取服务的入口
GetRequiredService<ICleanupJob>() 按注册找到 CleanupJob，并满足它的日志依赖
await job.RunAsync(...) 等这份任务执行完
await using 的右大括号 等待这个范围释放它管理的资源

缩进也要表达边界：var job 和 await job.RunAsync 同属 await using 里面；logger.LogInformation("本轮结束...") 在外面，因此打印它之前，Scope 已经释放。

CreateAsyncScope() 不是异步工厂调用；这里的“Async”主要对应后续异步释放能力。await using 的语法解释见第 4 章。

7. 三个常见错误，和 Orleans 的区别#

写法 问题 应该怎么做
Worker 构造参数直接写 Scoped 的 ICleanupJob Singleton 捕获 Scoped，范围错配 注入工厂，每轮在新 Scope 解析
把 CreateAsyncScope() 放到循环外 各轮共用同一份 Scoped 任务 需要每轮独立时，把创建放在循环体内
启动 job.RunAsync() 却不 await 就离开 Scope 任务还没结束，依赖可能已被释放 先等待任务完成，再结束范围

这里每一轮任务对应一个 Scope，是我们亲手规定的；普通 Orleans Grain 的 Scope 由运行时随一次激活管理，可能跨越很多次方法调用。不要因为看了 Worker 示例，就认为 Grain 每调用一次方法必须重新创建 Scope。

思考题：把 CreateAsyncScope 移到 while 外面，还是每轮新建任务吗？点击查看答案

不是。Scoped 的共享边界是 Scope，不是 while。若一直使用同一个 Scope，多轮解析会得到同一份任务。为了本例“每轮一份、及时释放”的目标，应当在每轮内部创建并结束范围。

思考题：IServiceScopeFactory 要不要自己 new，或再 AddSingleton？点击查看答案

不用。默认 DI 容器内置提供它。CleanupWorker 的构造参数声明需要该接口，容器在创建 Worker 时就会传入。你负责注册的是自己的 ICleanupJob 等业务服务。

1. 为什么不直接到处写字符串键？#

如果整个项目的业务代码都拼键名，很容易出现拼错、重复默认值、难以重构的问题。Options 模式把配置绑定到一个强类型类。

2. 完整示例#

将 appsettings.json 放在项目根目录，内容为上一章的 JSON。Program.cs：

C#
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;
using Microsoft.Extensions.Options;

var builder = Host.CreateApplicationBuilder(args);

builder.Services.Configure<GameOptions>(
    builder.Configuration.GetSection("Game"));

builder.Services.AddSingleton<RewardService>();

using var host = builder.Build();

var reward = host.Services.GetRequiredService<RewardService>();
Console.WriteLine(reward.Describe());

public sealed class GameOptions
{
    public int RewardCoins { get; set; }
    public string ServerName { get; set; } = "Unknown";
}

public sealed class RewardService
{
    private readonly IOptions<GameOptions> _options;

    public RewardService(IOptions<GameOptions> options)
    {
        _options = options;
    }

    public string Describe() =>
        $"{_options.Value.ServerName}：{_options.Value.RewardCoins} 金币";
}

关键读法：

C#
builder.Services.Configure<GameOptions>(
    builder.Configuration.GetSection("Game"));

这是登记 GameOptions 的配置规则；而构造函数里的 IOptions<GameOptions> 是访问这些配置值的服务。调用 _options.Value 才取得实际的 GameOptions 实例。

3. 三个选项接口的主要区别#

接口 DI 生命周期 典型用途 变化读取
IOptions<T> Singleton 不关心动态刷新的普通配置 Value 通常固定在创建后的值
IOptionsSnapshot<T> Scoped 在新 Scope 中读取配置快照 每个新 Scope 可以获取更新值
IOptionsMonitor<T> Singleton 在长寿命服务里关注最新配置 CurrentValue 可随支持刷新的配置源变化

特别注意 Orleans：IOptionsSnapshot<T> 的刷新边界是 Scope。Grain 的 Scope 通常持续整个激活周期，因此不能把它当作“每条 Grain 请求自动刷新配置”。如果需要长期运行的 Grain 读取较新配置，评估 IOptionsMonitor<T> 更合适。

4. 动态配置不等于自动远程配置#

IOptionsMonitor 读取变化依赖配置提供程序支持重新加载，以及应用实际触发或观察到重新加载。它不会凭空把一台机器上的 JSON 改动广播给整个 Orleans 集群。

1. Silo 是运行 Grain 的服务端节点#

Orleans 把一个或多个 Silo 组成集群。每个 Silo 是运行环境中的节点，可以管理许多 Grain 激活。服务端程序常用 .NET Host 集成启动 Silo。

2. Grain 是有身份的业务对象#

用游戏后端打比方：

文本
IPlayerGrain + Key=1001  → 玩家 1001
IPlayerGrain + Key=1002  → 玩家 1002
IGuildGrain  + Key=200  → 公会 200

Grain 类型和键共同帮助 Orleans 确定逻辑身份。一个玩家 Grain 不是一个网络连接，也不一定每时每刻占据一份内存对象。

3. Grain 引用是“调用入口”，不是必然已经创建的对象#

C#
var player = factory.GetGrain<IPlayerGrain>(1001);

这个 player 是能够向“玩家 1001”发起调用的 Grain 引用。调用 GetGrain 不等于执行了 new PlayerGrain()，也不要求玩家此刻已经激活。

C#
int coins = await player.GetCoinsAsync();

真正发起方法调用时，Orleans 会进行寻址、转发，并将请求交给已有激活或按需创建激活。

4. 一次激活（Activation）是一份正在运行的实例#

文本
玩家 1001 的逻辑 Grain 身份（可长期存在）
    ↓ 第一次调用
Silo A 创建一份 PlayerGrain 激活
    ↓ 处理很多次请求
空闲回收 / 节点变化等
    ↓ 以后再次调用
可能在 Silo B 创建新的 PlayerGrain 激活

所以“同一个玩家”≠“永远同一 C# 实例”。如果玩家的重要状态只保存在字段里，激活被回收后就可能失去这些内存数据。持久化要另行处理。

5. GetGrain 和 GetRequiredService 不是同一回事#

API 请求的对象 由谁控制身份和生命周期
provider.GetRequiredService<IRewardCalculator>() 普通 DI 服务 DI 容器的生命周期规则
grainFactory.GetGrain<IPlayerGrain>(1001) Grain 引用 Orleans Grain 身份与路由系统

这两套机制有关联，但不能混为一谈。

    private readonly IRewardCalculator _reward;
    private readonly ILogger<PlayerGrain> _logger;
    private readonly IPersistentState<PlayerState> _state;

    public PlayerGrain(
        IRewardCalculator reward,
        ILogger<PlayerGrain> logger,
        [PersistentState("player", "playerStore")]
        IPersistentState<PlayerState> state)
    {
        _reward = reward;
        _logger = logger;
        _state = state;
    }

    public Task<int> GetCoinsAsync()
    {
        return Task.FromResult(_state.State.Coins);
    }

    public async Task<int> ReceiveRewardAsync()
    {
        int amount = _reward.GetRewardCoins();
        _state.State.Coins += amount;

        await _state.WriteStateAsync();

        _logger.LogInformation(
            "玩家 {PlayerId} 金币变为 {Coins}",
            this.GetPrimaryKeyLong(),
            _state.State.Coins);

        return _state.State.Coins;
    }
}

1. 先懂用途：为什么需要放宽排队，而不是先学怎么加特性#

前面先讲了“加了特性可能出错”，却没有先解释“为什么有人还要加”。先把这件事说清楚：它们的作用是放宽同一个 Grain 激活的排队规则，让不必等待的请求不再陪着等待。

对你当前的钱包、背包、任务领奖逻辑：先不加这两个特性。只有说得清楚“哪种等待是多余的”“放进来的请求不会破坏什么业务规则”，再考虑开放。

先区分两种等待：有的必须等，有的没有必要

场景为什么等／为什么不用等本教材建议
同一钱包连续买两件商品第二次购买要依据正确余额，不能绕过第一次扣款的状态变化。先保留默认排队。
同一查询入口读取两名不同玩家的外部昵称两次查询只用各自参数，不改同一份业务状态。有排队瓶颈时，可考虑 [Reentrant]。
回放正在异步上传，界面需要查看进度进度查询的目的就是看中间过程，不应该等上传结束才回答。只为查询方法考虑 [AlwaysInterleave]。

它们究竟把哪条规则放宽了？

执行示意
默认：A 完成以后，B 才能开始。
开放交错：A 等待尚未完成的异步操作时，B 可以先执行一段。

[Reentrant]        整个 Grain 类的方法都允许这样交错。
[AlwaysInterleave] 只给选定的接口方法开放；它可以与其他请求交错。

这是“允许进入”，不是“多开线程”，也不是“自动保证安全”。 同一激活的同步代码段仍逐段执行；如果没有真正的异步等待，只是一直计算，不能靠这两个标记让当前计算被其他请求抢占。

[AlwaysInterleave] 是双向许可：它能在其他请求尚未完成时进入，其他请求也能在它尚未完成时进入。它不是优先级标记，更不是所有查询方法都该加的标配。

还有一个进阶用途：避免特定的互相等待

例如玩家 Grain A 等待房间 Grain B，而 B 又必须调用 A 取得昵称才能继续。两边都在等，就可能形成调用环。交错许可可以让某些回调继续执行。不过，优先考虑消除不必要的回调、直接把所需数据传给 B；确实需要回调时，也有范围更窄的调用链重入机制。 不要把“给所有 Grain 加 Reentrant”当成通用修复。

本节的默认排队均指：同一激活、普通请求、没有额外的交错或调用链重入配置。不同玩家的 Grain 可以各自工作，并不会因为玩家 1001 在等待而全体停下。

官方依据：请求调度：动机、交错范围与调用环；同步代码段仍然逐段执行。本节游戏场景、判断建议与模拟代码为教材补充，不是官方原文。

2. 什么时候考虑 Reentrant：两个互不依赖的外部查询#

先看需求：某个查询 Grain 充当外部资料查询入口。A 要查玩家 1001 的昵称，B 要查玩家 1002 的昵称。外部服务每次需要大约两秒，两次查询互不依赖。这里刻意让它们使用同一个查询 Grain，才能观察重入带来的区别。

不加时有什么不方便？

教学时间线
假设只有这两次请求，外部查询均耗时两秒：

默认非重入：
0 秒：开始查 1001，等待外部返回
2 秒：1001 返回；这时才开始查 1002
4 秒：1002 返回

允许交错：
0 秒：开始查 1001，等待外部返回
随后：开始查 1002，也等待外部返回
约 2 秒：两次结果陆续回来

减少的是“等前一件完成后才能开始”的时间。
不是把一次两秒的外部查询变成一秒。

时间线忽略网络、激活和调度开销，只是这个假设场景的推演，不是实测结果或吞吐量保证。下游限流、连接数及负载仍可能使请求变慢。

可以考虑使用的代码

下面是 Grain 类型定义，可放进已配置的 Orleans 服务端项目。Task.Delay 只是替身，让你不用接入真实外部平台就能观察等待；真实业务应替换为真正的异步查询。

C#
using Orleans;
using Orleans.Concurrency;

public interface INameQueryGrain : IGrainWithIntegerKey
{
    Task<string> GetNameAsync(long playerId);
}

// 这个类不保存玩家余额、库存等共享业务状态。
[Reentrant]
public sealed class NameQueryGrain : Grain, INameQueryGrain
{
    public async Task<string> GetNameAsync(long playerId)
    {
        // 模拟等待外部资料服务两秒；本例没有真的发送 HTTP 请求。
        await Task.Delay(TimeSpan.FromSeconds(2));

        // playerId 和 name 都属于这一次调用。
        string name = $"玩家 {playerId}";

        return name;
    }
}

调用方式同样重要

C#
// 两次调用故意发给同一个 Grain。
// GetGrain 的 1 是查询入口的键，不是下面要查询的玩家 ID。
var query = grainFactory.GetGrain<INameQueryGrain>(1);

Task<string> taskA = query.GetNameAsync(1001);
Task<string> taskB = query.GetNameAsync(1002);

// 先发出两次调用，再一起等待，才可以观察交错的价值。
string[] names = await Task.WhenAll(taskA, taskB);

Console.WriteLine(names[0]);
Console.WriteLine(names[1]);

这里 GetGrain(..., 1) 取得的是同一个查询入口；1001 和 1002 是两次调用的业务参数。如果你本来就调用两个不同玩家的 Grain，它们可以独立工作，不必为了“玩家之间并行”加 Reentrant。

C#
// 这种调用方式已经被调用方主动串行化了。
string nameA = await query.GetNameAsync(1001);
string nameB = await query.GetNameAsync(1002);

// B 必须等 A 返回后才会发出去。
// 即使 Grain 有 [Reentrant]，也不能让尚未发出的 B 提前执行。

为什么这个例子比较容易判断安全？

A 的 playerId 是 1001，B 的是 1002；它们各有自己的局部变量。代码没有共享的余额、库存，也没有跨等待保存的共享“当前玩家”。因此 A、B 不需要按业务顺序排队。

不要改成共享字段：如果把参数存入 _currentPlayerId，等待后再读取这个字段，B 就可能覆盖 A 的值。方法是“查询”也不自动安全；调用的服务、缓存、数据库上下文是否能承受重叠操作，也要一起检查。

适用条件是组合条件：多个请求确实命中同一激活，主要时间花在异步等待，彼此业务独立，依赖也支持重叠操作，并且确实希望改善排队。不是“没有字段就必须加”。

也不要为了使用这个特性，把所有玩家强行塞进同一个全局查询 Grain。按玩家／任务拆分本来就能获得独立调度；架构上不需要这个中间层时，不必为了示例专门添加它。

先判断，再看答案

把 [Reentrant] 删掉，查询还能正确返回吗？

查看答案与理由

能。在这个例子里，不加只会让同一激活内的两次查询排队，不会让业务失效。使用它是为了减少不必要的等待，而不是为了让异步方法能运行。

3. 什么时候考虑 AlwaysInterleave：导出时还要看进度#

先看需求：玩家请求导出一段回放，需要异步上传五份数据。上传期间，界面想显示 20%、40%、60% 的进度。

导出是一个长请求；进度查询是另一个请求。默认非重入会让普通进度查询等到导出完成再执行，最后才告诉你“100%”。 这个回答没错，但失去了进度条的用途。

只给进度查询开放，不把整个导出类开放

C#
using Orleans;
using Orleans.Concurrency;

public interface IReplayExportGrain : IGrainWithIntegerKey
{
    Task ExportAsync();

    // 特性写在接口方法上：允许进度查询与导出请求交错。
    [AlwaysInterleave]
    Task<int> GetProgressAsync();
}

// 整个类不加 [Reentrant]。
public sealed class ReplayExportGrain : Grain, IReplayExportGrain
{
    private int _progress;

    public async Task ExportAsync()
    {
        _progress = 0;

        for (int part = 1; part <= 5; part++)
        {
            // 模拟异步上传一段回放，实际项目替换为异步 I/O。
            await Task.Delay(TimeSpan.FromSeconds(1));

            _progress = part * 20;
        }
    }

    public Task<int> GetProgressAsync()
    {
        // 中间进度正是调用方想观察的内容。
        return Task.FromResult(_progress);
    }
}

这里 ExportAsync 不带特性，类也不带 [Reentrant]；两次普通导出请求仍按默认规则排队。只有 GetProgressAsync 获得与其他请求交错的许可。

调用方：启动后先观察，最后仍等待任务结果

C#
var export = grainFactory.GetGrain<IReplayExportGrain>(1);

// 先启动导出，但现在不等待整个导出完成。
Task exportTask = export.ExportAsync();

while (!exportTask.IsCompleted)
{
    await Task.Delay(TimeSpan.FromMilliseconds(600));

    int progress = await export.GetProgressAsync();
    Console.WriteLine($"回放导出进度：{progress}%");
}

// 仍然要等待任务并观察异常，不是把任务扔掉不管。
await exportTask;

可能看到 0%、20%、40%、60%、80%、100% 中的若干值；取决于采样时机，有的值会重复或跳过。删掉接口上的 [AlwaysInterleave] 再测试，第一次普通查询通常要等导出结束才返回。

它解决的具体问题
导出：上传第一段 → await 等待
查询：可以进入，读取当前进度

导出：第一段完成，进度改成 20%，再上传第二段 → await
查询：可以进入，读到 20%

导出：全部完成，进度改成 100%
查询：以后读到 100%

为什么这次允许看到“中间状态”？

因为中间状态就是这个接口承诺返回的内容。 进度 40% 不需要证明整个导出已经完成。此方法只读取一个瞬时值，并立即返回，没有先检查再等待后修改的过程。

但“查询钱包扣款后的最终余额”可能要求前面的保存已经成功；它和“当前上传进度”不是同一类查询。不能因为方法名字以 Get 开头，就全部加 AlwaysInterleave。

这个演示不是完整任务系统。进度仅存在本次激活内，没有断点恢复、持久化、任务去重或取消功能；第二次导出会排队后重新执行，不是自动拒绝。真实长任务还要设计任务 ID、状态持久化、超时和失败恢复；不要把代码变成无限时长、不观察异常的后台任务。

4. 什么时候先别用：钱包、库存、同步计算与四个判断问题#

先有需要解决的等待，再选择最小的开放范围。 能不开放就不开放；只需要一个状态查询，就不要把整个类设成可重入。

你的业务建议起点判断理由
玩家余额、扣款、背包数量、领取资格默认非重入请求之间通常有先后关系，要维护同一份状态。
同一笔奖励网络重试默认非重入 + 稳定业务 ID / 去重记录问题是“重复生效”，不是“请求进不来”。
互不依赖的异步外部查询证实同一激活存在等待瓶颈后，考虑 Reentrant允许多个外部等待重叠；须检查整个类及依赖。
异步任务的进度、明确允许中间态的诊断状态考虑给具体接口方法加 AlwaysInterleave观察过程，不要求等前一个业务彻底结束。
查询“必须等保存成功”的最终结果先保留默认排队／明确提交状态查询不写数据，也可能依赖前一请求已完成。
纯同步计算耗时、CPU 忙不要把重入当成加速办法同步代码不会因此被并行执行或抢占。
不同玩家 Grain 想同时处理通常不需要这两个特性不同激活本就有各自的调度；检查是否集中到了单一瓶颈。

钱包反例：两个购买都通过检查，为什么不该随意开放？

下面只演示风险，不是生产钱包实现。初始余额 100，两次独立购买都花 80；价格已由服务端验证为正数。

C#
// 反例片段：假设这是一个被错误标记为 [Reentrant] 的钱包。
// 初始余额为 100，两笔不同的购买各花 80。
public async Task<bool> BuyAsync(int price)
{
    if (_coins < price)
    {
        return false;
    }

    // 等待期间，另一个购买请求可能也通过余额检查。
    await Task.Delay(1000);

    _coins -= price;
    return true;
}
一种错误时序
A：余额 100，检查通过，等待
B：趁等待进入；余额还是 100，检查也通过，等待
A：恢复，扣 80，剩 20
B：恢复，再扣 80，变成 -60

如果保留默认非重入：
A 完成扣款后，B 才检查余额 20，于是 B 返回 false。

这里的重点不是“所有钱包都绝不能重入”，而是：这份实现依赖请求按顺序处理，你不能只加一个特性就把前提拿掉。 真实钱包还要处理持久化失败、重复请求、服务端鉴权等问题；非重入不是事务或防重复发奖机制。

四个问题，帮你决定该不该加

第一问：到底谁在等谁？ 是同一个激活内的后续请求被迫排队，还是外部服务本身慢？若是一次外部调用本身慢，重入不会缩短它。

第二问：后一个业务需要前一个业务的结果吗？ 如需要新余额、最新库存、成功保存的状态，优先保留顺序。

第三问：只开放一个方法，还是整个类都安全？ 进度查询只开放该方法；整个类都主要做相互独立的异步操作，才考虑 Reentrant。

第四问：在每个真正等待的 await 前后，别人改变状态会不会出错？ 检查字段、持久状态、缓存和注入依赖；说不清楚就先不加，别用“它仍然单线程”代替分析。

最适合你现在的默认选择：玩家 Grain 先不加；明确允许中间态的状态查询单独评估；独立查询 Grain 有实际排队瓶颈再考虑整类重入。很多功能完全不需要这两个特性。
补充：只有 async 或 Async 方法名，为什么还不够？

下面没有真正的异步等待。即使加 Reentrant，循环也会把当前同步代码段执行完，其他请求不会因此抢占这段计算。应该分析计算拆分、实体划分或计算工作调度，而不是把这个特性当作 CPU 并行开关。

C#
// 同步计算期间没有异步等待点。
// [Reentrant] 不会把这个循环拆到多个 CPU 核心上执行。
public Task<long> CalculateAsync()
{
    long result = 0;

    for (int i = 0; i < 10_000_000; i++)
    {
        result += i;
    }

    return Task.FromResult(result);
}
补充：循环调用是否必须加 Reentrant？

不一定。例如 A 等 B，B 为读取昵称又回调 A，可考虑由 A 直接把昵称传给 B，移除回调。确实必须回调时，官方还有 RequestContext.AllowCallChainReentrancy()，把许可限定在特定调用链的作用范围，而不是让整个类的所有普通请求都进入。它依然需要状态安全分析，不会自动解决数据库锁等其他死锁。

5. 默认非重入：await 暂停的是当前方法，不是整个服务器#

先把问题缩小：我们讨论的是同一个 Grain 的同一次激活，例如玩家 1001 当前运行的那个对象。 玩家 1002 是另一个激活，可以继续处理自己的请求。这里不讨论显式开放的调用链重入、特殊定时器交错、Task.Run 或逃离 Grain 调度器的代码。

C#
Task<int> requestA = player.AddCoinsAsync("A");
Task<int> requestB = player.AddCoinsAsync("B");

这里 A、B 是两次请求，即使调用的是同一个方法，它们也是两次独立调用。每次调用有自己的局部变量；两次调用访问的 _coins 字段，却是同一个玩家对象中的共享数据。

一次请求不等于一小段同步代码

C#
Console.WriteLine("第一段");

await Task.Delay(1000);

Console.WriteLine("第二段");

如果等待的任务还没有完成，当前方法会暂停，等待完成后再继续第二段。从第一段开始，到第二段执行完、方法返回，仍是同一次请求。 不要把“执行到 await”理解成“这次请求已经结束”。

await 不会阻塞等待它的线程；如果等待的任务已经完成，就可能直接继续，不发生暂停。有 await 语法，不代表每次一定会让出执行机会。

默认规则保留的是什么？

假设 A 已经开始，B 又到达同一个激活：

执行顺序 / 输出
A：执行第一段
A：等待异步结果 ───────────────┐
B：到达，但等待 A 请求结束     │
A：恢复，执行第二段 ◀─────────┘
A：方法返回，请求结束
B：现在才开始执行

等待时，线程可以去执行其他工作，其他玩家的 Grain 也可以运行。被保留的是这个激活接纳另一个普通请求的名额，不是把一个线程锁在那里干等。

先记一句：默认非重入是“同一个激活的普通请求，前一件办完，再开始下一件”；不是“整个 Silo 一次只能做一件事”。

官方依据：Orleans 调度概览、C# await 运算符。后面的金币例子是为本教材编写的教学示例，不是官方原文。

6. 用两次加金币请求观察默认排队：100 → 200 → 300#

这个实验故意把“读取旧金币”和“写回新金币”分放在 await 两侧。它用来观察调度，不是建议你在真实业务里这样拆分更新。 初始金币为 100，每次调用再加 100。

Grain 接口和实现

C#
using Orleans;

public interface IPlayerGrain : IGrainWithIntegerKey
{
    Task<int> AddCoinsAsync(string requestName);
    Task<int> GetCoinsAsync();
}

// 没有加 [Reentrant]：使用默认的非重入调度。
public sealed class PlayerGrain : Grain, IPlayerGrain
{
    private int _coins = 100;

    public async Task<int> AddCoinsAsync(string requestName)
    {
        int oldCoins = _coins;

        Console.WriteLine(
            $"{requestName}：读到 {oldCoins}");

        // 仅模拟一个尚未完成的异步操作，不是真的存数据库。
        await Task.Delay(TimeSpan.FromSeconds(2));

        _coins = oldCoins + 100;

        Console.WriteLine(
            $"{requestName}：写回 {_coins}");

        return _coins;
    }

    public Task<int> GetCoinsAsync()
    {
        return Task.FromResult(_coins);
    }
}

C#

await player.AddCoinsAsync("B");

后一种写法是调用端主动等 A 完成后才发送 B，两次请求根本没有重叠，因此无法用它看出是否允许重入。

假设 A 先被处理，正常结果是这样

执行顺序 / 输出
A：读到 100
A：写回 200
B：读到 200
B：写回 300
最终余额：300
步骤 A 自己的 oldCoins B 自己的 oldCoins 共享字段 _coins

A 读值后等待 100 B 尚未开始 100

A 的局部变量不会“传给 B”。B 开始时会重新读取共享字段，所以它读到的是 200。 本节不承诺不同调用者之间的全局先到先服务顺序；交换 A、B 的先后，结论仍是两个请求不交错、最终加两次。

7. [Reentrant]：整类允许交错，但不是同一个激活多线程并行#

[Reentrant] 是一个 C# 特性，可以理解为给 Orleans 看的调度标记。它来自 Orleans.Concurrency，应标在 Grain 实现类上。

只改上一节的类声明

C#
using Orleans.Concurrency;

// 加在原来的 PlayerGrain 类上，方法体保持上一节不变。
// 不要在同一个项目中再定义一份同名 PlayerGrain。
[Reentrant]
public sealed class PlayerGrain : Grain, IPlayerGrain
{
    // 这里保留上一节的字段、AddCoinsAsync 和 GetCoinsAsync。
}

这段只是展示修改位置，不是可以替换整个类的完整实现。它告诉 Orleans：

这个激活已经有一个请求没完成时，也允许开始其他请求。每一小段代码仍然依次执行，但不同请求的代码段可以轮流执行。

也包括对同一个方法的两次调用，不要求 A、B 是不同的方法。

仍然发出 A、B，就可能出现下面的顺序

执行顺序 / 输出
A：读到 100
A：await，暂时等待
B：读到 100
B：await，暂时等待
A：恢复，写回 100 + 100 = 200
B：恢复，写回 100 + 100 = 200
最终余额：200，而不是应有的 300
步骤 A 的 oldCoins B 的 oldCoins 共享字段 _coins
A 读取后暂停 100 尚未赋值 100
B 读取后暂停 100 100 100
A 写回 100 100 200
B 写回 100 100 200

B 保存的 oldCoins 是自己早先读到的 100，不会因为 A 把 _coins 改成 200 而自动变成 200。 两次赋值都写了 200，于是少算了一次奖励。这叫丢失更新。

这是一种允许出现的错误时序，不是“每次运行都保证得到 200”。如果 B 很晚才开始，也可能读到 200。正因为错误依赖时序，不能用“一次运行没出错”证明逻辑安全。

为什么没有两条线程同时执行，也会错？

错误来自“读取后，等了一会儿，再按旧值写回”。在这段等待时间里，另一件事改变了共享数据。并发逻辑错误不要求两条线程在同一瞬间同时改字段。

不要把 [Reentrant] 当成加速按钮。它适合已分析清楚状态关系的异步业务；它不会让 CPU 计算在同一个激活里自动并行，也不会提供事务。

官方依据：ReentrantAttribute（Orleans 10）、单线程任务调度。微软迁移指南也用跨 await 的计数器示例说明这一类风险。

8. [AlwaysInterleave]：只开放指定方法，并且允许双向交错#

假设你不希望“发奖励 A”和“发奖励 B”互相交错，但希望发奖励正在等待时，仍能查询“当前是否正在保存”。这时可以把那个查询方法标成 [AlwaysInterleave]，而不是让整个类都重入。

放置位置不同：[Reentrant] 标在实现类上；[AlwaysInterleave] 标在 Grain 接口的方法上。

完整的小例子

C#
using Orleans;
using Orleans.Concurrency;

public interface IWalletGrain : IGrainWithIntegerKey
{
    Task AddCoinsAsync(int amount);

    // 普通方法：仍遵守默认的非重入规则。
    Task<int> GetCoinsAsync();

    // 注意：标在 Grain 接口的方法上。
    [AlwaysInterleave]
    Task<string> GetStatusAsync();
}

// 整个类没有加 [Reentrant]。
public sealed class WalletGrain : Grain, IWalletGrain
{
    private int _coins = 100;
    private bool _saving;

    public async Task AddCoinsAsync(int amount)
    {
        if (amount <= 0)
        {
            throw new ArgumentOutOfRangeException(nameof(amount));
        }

        _coins = checked(_coins + amount);
        _saving = true;

        try
        {
            // 只是模拟等待保存；本示例没有真正写入数据库。
            await Task.Delay(TimeSpan.FromSeconds(3));
        }
        finally
        {
            _saving = false;
        }
    }

    public Task<int> GetCoinsAsync()
    {
        return Task.FromResult(_coins);
    }

    public Task<string> GetStatusAsync()
    {
        return Task.FromResult(
            $"内存金币：{_coins}，正在等待保存：{_saving}");
    }
}

在第一个调用尚未结束时再查询

C#
var wallet = grainFactory.GetGrain<IWalletGrain>(1001);

Task saveTask = wallet.AddCoinsAsync(100);

// 给第一个请求留出进入等待的时间。
// 这只是演示时序，不是生产代码的同步手段。
await Task.Delay(200);

// 普通方法：如果 AddCoinsAsync 仍未结束，就需要等待。

// 特殊方法：允许在 AddCoinsAsync 尚未结束时执行。
string status = await wallet.GetStatusAsync();
Console.WriteLine(status);

await saveTask;
Console.WriteLine(await balanceTask);

当查询确实到达三秒等待区间内时，状态可能是：

执行顺序 / 输出
GetStatusAsync：
内存金币：200，正在等待保存：True

AddCoinsAsync 完成之后：
普通 GetCoinsAsync 返回 200

GetCoinsAsync() 虽然也只读取数据，但没有标记时，不会仅因为方法名是 Get 就自动获得交错资格。

两个普通请求会不会因此也都“放行”？

不会。假设类没有 [Reentrant]，也没有其他重入设置：

这两个请求 是否允许互相交错
普通 AddCoinsAsync A 与普通 AddCoinsAsync B 不允许
普通 AddCoinsAsync 与带标记的 GetStatusAsync 允许
带标记的 GetStatusAsync 与普通 AddCoinsAsync 允许
两次带标记的 GetStatusAsync 允许

这里说的是请求之间的相容关系，不是绕过所有排队限制。如果 A 这个普通写请求仍在运行，不能因为旁边还有一个带标记的查询，就让另一个普通写请求 B 绕过 A。

“双向”是什么意思？

若带标记的方法自己也有 await：

C#
// 接口中的 GetStatusAsync 仍带有 [AlwaysInterleave]。
public async Task<string> GetStatusAsync()
{
    int before = _coins;

    await Task.Delay(1000);

    int after = _coins;

    return $"等待前：{before}，等待后：{after}";
}

它等待时，也可能执行一个普通写请求，所以 before 和 after 不一定相同。不仅是“它可以进入其他请求的等待期间”，也是“其他请求可以进入它的等待期间”。

名称里的 Always 不等于什么？

它不等于最高优先级、不等于立即执行，也不会打断正在运行的一段同步代码。它更不代表“读到的都是已持久化数据”。本例查询返回的是内存状态，可能还处于业务流程中间。

[AlwaysInterleave] 也不强制只读。不应给任意发奖、扣款方法随手加它。另一个 [ReadOnly] 特性主要允许只读请求之间交错，并不等价于允许穿过写请求。

官方依据：AlwaysInterleaveAttribute 的含义与接口标注位置、方法级交错与只读方法。

9. 回到原来的 WriteStateAsync：等待保存时究竟发生了什么？#

你截图中的方法是：

C#
public async Task<int> ReceiveRewardAsync()
{
    int amount = _reward.GetRewardCoins();

    // 第一步：先修改当前激活中的内存数据。
    _state.State.Coins += amount;

    // 第二步：发起保存，并等待保存操作结束。
    await _state.WriteStateAsync();

    // 第三步：保存成功后，读取此刻的内存余额并返回。
    return _state.State.Coins;
}

默认非重入时

假设初始 100，每次奖励 100，A 先执行，并且两个保存都成功：

执行顺序 / 输出
A：内存改成 200 → 等待写入 → 返回 200
B：这时才开始
B：内存改成 300 → 等待写入 → 返回 300

A 等待时，B 不会只因为看到一个 await 就获得执行资格。A 的异步写入结束后，A 自己的后续代码仍能恢复，不会被误当成一个必须等待自己结束的新请求。

允许重入时：不要把这个例子和“丢失更新”混为一谈

这个方法的 _state.State.Coins += amount 在 await 之前，没有把读取与写回拆到两侧。在 Grain 调度器的同一段同步执行中，不会在这句的读写中间突然插入另一个 Grain 请求。

因此，加上 [Reentrant] 并不意味着这句加法一定丢金币。 真正需要重新检查的是：写入能否重叠、业务状态能否被中途观察，以及返回值代表哪个时刻。

例如以下是可能的内存时序：

执行顺序 / 输出
A：内存改成 200，开始等待写入
B：内存改成 300，也开始等待
A：写入结束，执行 return _state.State.Coins
A：此刻可能读到 300，而不是自己刚加完时的 200

这只是说明返回值取的是恢复执行时的共享状态。它不证明磁盘一定已是 300，也不规定两个写入的提交顺序。具体存储提供程序如何处理并发写入、版本号和冲突，还必须另行核对。

把本次计算结果保存到局部变量再返回，只解决“返回哪个数”的问题；不会自动解决重叠保存、业务去重或事务问题。对当前这个入门玩家钱包，优先保持默认非重入更容易推理。

官方依据：Grain 状态读写与故障、请求交错规则。这里的 A/B 时序为对本教材原代码的分析。

10. 两类安全问题：少算一次，与同一笔重复发放，是两回事#

把两个问题放到同一个“初始 100，每笔奖励 100”的例子里：

问题 请求代表什么 正确结果 错误结果示例
并发安全 A、B 是两笔不同且有效的奖励 300 两次读旧值、相互覆盖，最后只有 200
业务幂等 A、B 是同一笔奖励的第一次发送与重试 200 被当成两笔处理，最后变成 300

并发安全：两笔不同的事，都应该正确生效

上一节 [Reentrant] 例子里的核心错误就是：

C#
int oldCoins = _coins;

await Task.Delay(2000);

// oldCoins 可能已经过时。
_coins = oldCoins + 100;

对这个纯内存加法实验，一种更窄的改法是：

C#
await Task.Delay(2000);

// 在恢复后的同一段同步代码里，读取当前值并完成加法。
// 只说明这个加法不再使用旧快照；不是通用事务方案。
_coins = checked(_coins + 100);

return _coins;

但不能把“把 await 往前挪”当成所有业务的万能修复。例如扣金币时，余额检查也要和扣减放到合适的同一段执行中，不能先检查余额足够、等待后还相信旧判断。真实持久化操作还涉及写入顺序和故障恢复。

对现在的入门钱包，更直接的选择是保持默认非重入，并让每个请求等待自己的异步工作完成。

业务幂等：同一笔事，重试不能再生效一次

回到最简单的、不带任何重入标记的代码：

C#
public Task<int> ReceiveRewardAsync()
{
    _coins += 100;

    return Task.FromResult(_coins);
}

调用端顺序调用两次：

C#
await player.ReceiveRewardAsync();  // 100 -> 200

// 第一次可能已经成功，但调用方没收到响应，于是重试。
await player.ReceiveRewardAsync();  // 200 -> 300

这里甚至没有并发、没有交错、没有 await 中间窗口，仍会重复发钱。因为服务端没有收到“这是同一笔奖励”的业务标识，它只知道方法被调用了两次。

一个典型的重复业务过程：

执行顺序 / 输出
服务端：发奖并保存成功
网络：成功响应没有送到调用方
调用方：不知道结果，再发送同一笔业务
服务端：必须识别这笔业务已完成，而不是再加一次钱

Orleans 默认的“消息至多投递一次”与“同一笔业务只发奖一次”不是同一层保证。调用方主动重试、网关重复提交或重复点击，都可能产生新的调用，业务仍需要自己的去重规则。

官方依据：Orleans 消息投递保证。金币数值和反例是本教材的教学分析。

11. 给同一笔奖励一个稳定编号：用代码实现内存去重#

先不同时引入数据库，把“识别同一笔业务”的逻辑看清楚。

假设本例每笔合法奖励固定发 100 金币。每笔奖励有稳定的业务编号，例如 quest-1001-completion-001。重试必须沿用原编号；每重试一次就生成一个新编号，等于告诉服务端“这是另一笔新业务”。

C#
using Orleans;

public interface IRewardGrain : IGrainWithIntegerKey
{
    Task<int> ClaimRewardAsync(string rewardId);
}

// 保持默认非重入；这里只演示内存中的去重逻辑。
public sealed class RewardGrain : Grain, IRewardGrain
{
    private int _coins = 100;

    // 奖励编号 -> 第一次发奖后的余额结果。
    private readonly Dictionary<string, int> _receipts = new();

    public Task<int> ClaimRewardAsync(string rewardId)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(rewardId);

        // 1. 这笔奖励发过：返回第一次的结果，不再加钱。
        if (_receipts.TryGetValue(rewardId, out int originalResult))
        {
            return Task.FromResult(originalResult);
        }

        // 2. 这笔奖励没发过：本例由服务器固定发 100 金币。
        int newBalance = checked(_coins + 100);

        // 3. 更新余额，并记住这笔奖励的处理结果。
        _coins = newBalance;
        _receipts.Add(rewardId, newBalance);

        return Task.FromResult(newBalance);
    }
}

300  // 编号 002：另一笔奖励，再发一次

注意：字典保存的是原请求的结果。以后即使余额又变了，重试旧编号仍返回旧收据，而不是承诺返回当前余额。需要当前余额时，可以另设查询方法。

为什么这还不是完整的生产方案？

这份字典只在当前激活的内存中。激活被回收或进程重启后，记录会丢失；所以它只用来解释幂等判断。下一节才把余额和收据一起交给持久化状态。

示例也假设这是一个已经校验过资格的内部发奖入口。真实客户端不能靠随便编一个新 rewardId 就领钱：服务端需要验证奖励归属、领取资格和奖励内容。业务编号可以来自服务端的任务完成记录、结算流水等。

“先查字典，再等待”为什么又可能出问题？

C#
// 反例：如果这个请求允许交错，这个判断可能被两次请求一起通过。
if (!_receipts.ContainsKey(rewardId))
{
    await ValidateRewardAsync(rewardId);

    // 两次请求都可能认为自己是首次处理。
    // 必须在此处重新判断，或设计明确的进行中状态/串行处理规则。
}

ValidateRewardAsync 在这里是说明问题的占位方法，并非框架 API。加入去重记录，并不意味着可以随意开启重入；“检查—等待—修改”的流程仍需要保证一致性。

设计依据：持久化故障与幂等命令重试。本节实现是特意限制在单激活内存范围的教学方案。

12. 进一步保存余额与收据：成功路径、失败路径都要说明#

这一节是在前面的内存示例上加持久化，不是对任意数据库、任意网络故障都保证“恰好一次”的万能模板。

假设：发奖请求默认非重入；只有这个方法修改这份状态；存储提供程序支持对该状态记录作一致的整体读写；没有额外的外部支付、消息发送或跨 Grain 转账。

状态、接口与 Grain

C#
using Orleans;
using Orleans.Runtime;

[GenerateSerializer]
public sealed class RewardState
{
    [Id(0)]
    public int Coins { get; set; } = 100;

    [Id(1)]
    public Dictionary<string, int> Receipts { get; set; } = new();
}

public interface IPersistentRewardGrain : IGrainWithIntegerKey
{
    Task<int> ClaimRewardAsync(string rewardId);
}

// 不加 [Reentrant]；也不开放可以观察或修改这份状态的交错方法。
public sealed class PersistentRewardGrain : Grain, IPersistentRewardGrain
{
    private readonly IPersistentState<RewardState> _state;

    // 写入失败后，禁止直接相信已经修改过的内存状态。
    private bool _mustReload;

    public PersistentRewardGrain(
        [PersistentState("rewards", "playerStore")]
        IPersistentState<RewardState> state)
    {
        _state = state;
    }

    public async Task<int> ClaimRewardAsync(string rewardId)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(rewardId);

        if (_mustReload)
        {
            // 读取失败会继续抛异常，标记不会被清除。
            await _state.ReadStateAsync();
            _mustReload = false;
        }

        RewardState current = _state.State;

        if (current.Receipts.TryGetValue(
            rewardId,
            out int originalResult))
        {
            return originalResult;
        }

        int newBalance = checked(current.Coins + 100);

        // 把“新余额”和“这笔奖励已处理”放进同一份待写状态。
        var next = new RewardState
        {
            Coins = newBalance,
            Receipts = new Dictionary<string, int>(current.Receipts)
        };

        next.Receipts.Add(rewardId, newBalance);
        _state.State = next;

        try
        {
            await _state.WriteStateAsync();
        }
        catch
        {
            _mustReload = true;

            // 不能吞掉异常后宣称成功，也不能认定一定没写进去。
            throw;
        }

        return newBalance;
    }
}

这个版本有三处关键变化

余额与收据一起保存。 不能先只保存余额，随后才单独保存“已处理”标记；中途故障可能留下“钱已加、标记没加”的状态。

成功后才返回成功结果。 WriteStateAsync() 抛异常时，异常继续传给调用方，不把内存中的新结果冒充持久化成功。

失败后不继续相信旧的内存视图。 _mustReload 会迫使后续调用先重新读取状态；读取失败仍拒绝继续。上例只有一个公开业务方法，新增其他读写方法也必须遵守相同的恢复门槛。

写入超时为什么不能简单回滚？

超时可能意味着“没写入”，也可能是“已经写入，但确认响应丢了”。因此，直接把金币减回去、删除收据并重试，不一定正确。

重新读取只是恢复步骤之一。遇到结果不确定、旧写入仍可能完成、读取不是强一致，或者有外部副作用时，需要结合提供程序的版本控制、事务与对账设计。 不能仅凭这段示例宣称已经解决所有分布式一致性问题。

另外，收据集合会增长；清理策略必须与允许重试的时间窗口配套，不能删除记录后又接受无限期旧请求。跨多个状态记录的原子更新、发奖后发布消息等，也不在本例保证范围内。

官方依据：IPersistentState、显式读取与写入错误、单记录持久化边界、故障语义与应用级幂等。代码为教学扩展示例。

13. 不要在构造函数里读取尚未加载的 State#

构造函数拿到的是状态访问对象，不代表它已经把持久化数据读取完毕。构造函数里保存引用即可：

C#
public PlayerGrain(
    [PersistentState("player", "playerStore")]
    IPersistentState<PlayerState> state)
{
    _state = state;

    // 不要在这里根据 _state.State.Coins 决定玩家真实余额。
}

需要根据已经加载的状态初始化业务时，放到 OnActivateAsync 等适当的激活阶段。重要变更要在业务流程中显式保存；进程崩溃时，不能指望停用回调一定执行。

这件事与本章的重入问题是两条不同的轴线：激活阶段决定状态什么时候准备好；请求调度决定准备好以后，哪些调用能互相交错。

官方依据：Grain 持久化与激活时的状态读取。

        if (amount <= 0)
        {
            throw new ArgumentOutOfRangeException(nameof(amount));
        }

        _coins = checked(_coins + amount);
        _saving = true;

        try
        {
            // 只是模拟等待保存；本示例没有真正写入数据库。
            await Task.Delay(TimeSpan.FromSeconds(3));
        }
        finally
        {
            _saving = false;
        }
    }

    public Task<int> GetCoinsAsync()
    {
        return Task.FromResult(_coins);
    }

    public Task<string> GetStatusAsync()
    {
        return Task.FromResult(
            $"内存金币：{_coins}，正在等待保存：{_saving}");
    }
}

public interface INoDedupRewardGrain : IGrainWithIntegerKey
{
    Task<int> ReceiveRewardAsync();
}

// 没有 Reentrant，也没有 AlwaysInterleave。
public sealed class NoDedupRewardGrain : Grain, INoDedupRewardGrain
{
    private int _coins = 100;

    public Task<int> ReceiveRewardAsync()
    {
        _coins = checked(_coins + 100);

        return Task.FromResult(_coins);
    }
}

public interface IRewardGrain : IGrainWithIntegerKey
{
    Task<int> ClaimRewardAsync(string rewardId);
}

// 保持默认非重入；这里只演示内存中的去重逻辑。
public sealed class RewardGrain : Grain, IRewardGrain
{
    private int _coins = 100;

    // 奖励编号 -> 第一次发奖后的余额结果。
    private readonly Dictionary<string, int> _receipts = new();

    public Task<int> ClaimRewardAsync(string rewardId)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(rewardId);

        // 1. 这笔奖励发过：返回第一次的结果，不再加钱。
        if (_receipts.TryGetValue(rewardId, out int originalResult))
        {
            return Task.FromResult(originalResult);
        }

        // 2. 这笔奖励没发过：本例由服务器固定发 100 金币。
        int newBalance = checked(_coins + 100);

        // 3. 更新余额，并记住这笔奖励的处理结果。
        _coins = newBalance;
        _receipts.Add(rewardId, newBalance);

        return Task.FromResult(newBalance);
    }
}

15. 思考题、参考答案与这一章应该记住的结论#

思考题一：加上 Reentrant，是否就是两条线程一起修改这个 Grain？

查看答案

不是。在 Grain 调度器内，同一个激活一次只执行一段同步代码。变化的是：A 请求未结束时，可以执行 B 的某个代码段。因此 A 在 await 之后不能继续无条件相信等待前读到的共享状态。

思考题二：GetStatusAsync 带 AlwaysInterleave，两个普通 AddCoinsAsync 是否也能互相交错？

查看答案

不会仅因为存在这个查询方法，就把整个 Grain 变成 Reentrant。GetStatusAsync 与普通请求可以交错；两个普通请求彼此仍按默认规则排队。若同时还有其他阻塞的普通请求，不能借着查询的标记绕过它。

思考题三：默认非重入是不是就不会重复发奖？

查看答案

不是。它能让两次普通调用先后处理，但不会自动知道这两次调用代表同一笔奖励。两次都执行“加 100”，仍然会加两次。需要稳定的业务编号、去重记录，以及合适的持久化和失败处理。

思考题四：截图中的加法位于 await 前，是否必然发生丢失更新？

查看答案

不是。截图没有把读旧值和写回分到 await 两侧。允许交错后更直接的问题是：后续 return 可能读取到另一个请求改过的余额，以及多个写入如何排序和处理失败。要分析具体代码，不能把所有含 await 的方法都当成同一种错误。

给当前玩家钱包的选择

先保持默认非重入；不要为了“更快”给所有 Grain 加 [Reentrant]。 有明确需求再选择最小范围的交错，并检查每一个等待点前后的状态假设。展示进度的查询也必须允许读到中间状态，不能把它当作已提交余额凭证。

并发安全：不同的有效业务都要正确生效。业务幂等：同一笔业务重试，不能重复生效。 两者缺一不可，也都不等于数据库事务已经自动做好了。

官方资料

  • 请求调度：默认行为、Reentrant、AlwaysInterleave、ReadOnly
  • 任务调度：一次只执行一个代码段，不固定绑在同一线程
  • ReentrantAttribute（Orleans 10）
  • AlwaysInterleaveAttribute（Orleans 10）
  • 消息投递保证与重试
  • 状态持久化与失败处理
