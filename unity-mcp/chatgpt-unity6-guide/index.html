连接原理：三段链路

ChatGPT Desktop发起 MCP 工具调用
→
MCP HTTP Server127.0.0.1:8080/mcp
↔
Unity 6 EditorSession Active

Unity 端使用 HTTP Local 传输，由 Unity 插件负责启动本地 MCP Server。ChatGPT 通过 Streamable HTTP 访问该服务。由于服务已经由 Unity 管理，因此 ChatGPT 端无需再配置 uvx 的 STDIO 启动命令。

两个地址不要混淆： Unity 插件界面显示 http://127.0.0.1:8080；ChatGPT MCP 客户端填写 http://127.0.0.1:8080/mcp（带 /mcp 路径）。

准备 Windows 环境

安装 uv / uvx

uv 管理 Python 版本、项目依赖和虚拟环境，uvx 是它内置的独立工具运行命令（相当于 uv tool run）。只安装 uv 就会包含 uvx。

CMD / PowerShell · 安装 uv 
winget install --id astral-sh.uv -e
CMD · 验证 
uv --version
uvx --version
where uvx

安装 Python 3.12

本次已经安装了 Python 3.12.15。uv 可以自动下载对应版本，无需手动安装 Python 官方安装包。

CMD · Python 安装与查看 
uv python install 3.12
uv python list --only-installed
uv python find 3.12
重要： python --version 看起来切换到 3.12，不等于 uvx 必然选择 3.12。这正是本次排错的关键，详见后文“PyYAML 构建失败”章节。

让 CMD 直接使用 Python

当 where python 只输出 WindowsApps 别名时，可能导致 python --version 没有预期结果。本次使用 uv 提供的默认可执行文件入口成功解决。

CMD · 默认 Python 与 PATH 
uv python install 3.12 --default --preview-features python-install-default
uv python update-shell

关闭并重开终端，使用 where python 和 python --version 检查。--default 在本次 uv 版本中属于预览功能；它管理的是 Windows 的 python.exe 入口。

本次真实故障：PyYAML 构建失败

在 Unity MCP 初次自动启动阶段，日志曾显示服务器无法访问：

失败日志 · 关键片段 
MCP-FOR-UNITY: Local HTTP server did not become reachable.
Building pyyaml==6.0.3
error: Failed to build `pyyaml==6.0.3`
...
build\lib.win-amd64-cpython-315
...
error: Microsoft Visual C++ 14.0 or greater is required.

问题的准确含义

当时 uvx 为 MCP Server 安装依赖时选择了 Python 3.15（日志中的 cpython-315），PyYAML 6.0.3 因该执行环境没有使用适合的二进制包而尝试源码编译；系统缺少 C++ 编译工具链，最终导致启动失败。

这与 Unity Setup 显示 Python 3.12 绿色并不矛盾：Setup 检查系统可见的 Python；uvx 作为独立工具运行器会自行解析解释器版本。 本次日志能证明失败使用了 3.15，但不能仅凭它断言所有 uvx 版本选择都只由单一配置项决定。

实际采用的解决办法

本次已经把系统默认的 Python 入口切换到 3.12，并通过 uv 的全局版本配置让 uvx 更容易选择兼容的 3.12，然后重启 Unity 内的 Server，最终得到 Server ready 和 Session connected。

CMD · 建议操作 
uv python install 3.12
uv python pin --global 3.12
uv python pin --global
uv python list --only-installed

再次点击 Unity MCP 的 Start Server。如果启动成功，无需安装 C++ Build Tools。uv python pin --global 是 uv 的全局版本偏好，不等同于修改 python.exe 的 Windows PATH 入口。

为什么不推荐设置全局 UV_PYTHON=3.12？ 这会给继承该环境变量的其他 uv 命令施加版本要求，不利于经常切换多个 Python 版本的开发习惯。当前已通过更常规的方式解决问题，没有必要设置该变量。

如果以后再次出现相同错误

  1. 在 Connect 查看是否出现 Server ready 与绿色 Session。
  2. 检查 Unity Console 错误和项目中的 Library/MCPForUnity/Logs/server-launch-8080.log。
  3. 如果仍有 cpython-315，确认 uv python pin --global 的结果；同时检查当前项目下是否存在覆盖它的 .python-version，以及是否设置了 UV_PYTHON。
  4. 如需精确验证版本，可临时运行带 uvx --python 3.12 的诊断命令，但这只是排查手段，不是日常的启动要求。
  5. 如选择正确的 Python 后依然需要源码编译，再评估依赖版本及 C++ Build Tools，不要一开始就安装大型编译工具链。

Server 已运行但显示 No Session

如果已出现 Stop Server 按钮，但下方仍有红点 No Session，可点击右侧的 Connect。本次就是在该步骤之后出现绿色 Session Active (DemoUnityProject)。

ChatGPT 保存成功但不能调用工具

依次核对：Unity 仍在运行 → Session Active → ChatGPT 服务器处于启用状态 → 类型是流式 HTTP → URL 为 http://127.0.0.1:8080/mcp → 新建会话实际调用工具。不要将“保存配置无错误”误认为“工具调用成功”。

安全使用建议

  • 对场景、Prefab、资源的批量改动，先提交 Git 或建立备份。
  • 区分只读查询与会修改文件的工具调用，明确要求“不要修改其他内容”。
  • 出现异常时优先核对 Unity Console、MCP Session、工作区 Diff，而不只是接受 AI 的自然语言描述。
  • 在真实 iOS / Android 打包或清理资源前检查构建目标与输出目录。
工作区变更提示： 如果 ChatGPT Work 显示了大量代码变更，不要仅凭计数推断是 MCP 读取引起的；应先查看 Git Diff，确认变更来源。

常见问题

为什么返回的场景没有 GameObject？

空场景可能返回根 GameObject 数量为 0，这不代表 MCP 出错。如果期望读取其他场景，请先在 Unity 中打开目标场景后重新查询。

是否必须固定全局 UV_PYTHON？

不需要。本次成功接入没有依赖常驻 UV_PYTHON=3.12。优先保持 uv 的全局版本偏好与具体项目配置清晰，必要时对单个工具进程显式指定 Python。

HTTP Local 是否需要公网服务器？

不需要。本次地址是 127.0.0.1（回环地址），ChatGPT 桌面客户端与 Unity 都运行在同一台 Windows 电脑上。不要把此地址误用于另一台机器的客户端。

Unity 重启后需要重新安装吗？

通常不需要重新安装 Package。重新打开 Unity 项目后，再在 MCP for Unity 窗口启动 Server、确认 Session Active，并检查 ChatGPT 的 unity-mcp 是否可用即可。

Unity AI 和 Unity MCP 是一回事吗？

不是。Unity AI 偏向 Unity 官方在编辑器内提供的 AI 能力；MCP for Unity 则通过 MCP 协议让 ChatGPT 等外部客户端访问编辑器工具。本文记录的是后者的接入流程。
